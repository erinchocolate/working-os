# skill: 系统复盘 —— 从 recurring 晋升认知资产 + 改进系统本身

**触发**：
- 「系统复盘」→ 对本系统做一次复盘。
- 「系统复盘 <日期>」→ 复盘指定周期。
- 定期（每 1-2 周）主人主动触发。

**目的**：两件事合一做——从 `reviews/recurring.md` 中晋升认知资产到 `assets/`，同时检查系统本身的摩擦点并改进。

## 先读
1. `AGENTS.md` —— 系统现状与约定。
2. `reviews/recurring.md` —— 候选池现状（核心输入）。
3. `assets/INDEX.md` —— 已有资产，避免重复。
4. 近期 `worklog/` —— 了解近期活动量和主题。
5. `skills/` 目录 —— 有哪些工作流可被改。

## 流程一：晋升认知资产

1. 读 `reviews/recurring.md`，找 **count ≥ 2 且跨 2+ 情境/项目** 的条目。
2. 对每条符合条件的候选：
   - 向主人提名：说明 pattern 是什么、出现了几次、在哪些情境出现。
   - 主人确认 → 写入 `assets/` 对应文件（mental-models.md / pitfalls.md / mirror.md），更新 `assets/INDEX.md`。在 recurring 中标 `status: 已晋升`。
   - 主人否决 → 在 recurring 中标 `status: 已搁置`，不再提名。
3. **不晋升的**：count = 1 的条目不提名，留待下次收工时追加新 evidence。

## 流程二：检查系统摩擦

1. 回顾近期使用情况：
   - worklog 篇数（收工有没有真发生）。
   - recurring 条目增长（认知提炼有没有在跑）。
   - assets 晋升数。
   - projects context 有没有变厚（摄取/执行回写有没有真发生）。
   - 哪些 skill 用过、哪些一次没碰。
2. 三问：
   - 这周期哪一次，加载 context/assets 真的省了时间？
   - 这周期哪一次，用 skill 反而比直接干还累？
   - 这周期有没有一条认知或信号，系统没接住？
3. 针对摩擦点提出改动（删一步、改触发、调先读、加原则等）。停下来问主人确认后才改文件。

## 流程三：记账

写 `reviews/system/<日期>.md`：
```
- 飞轮信号: worklog N 篇 / recurring +M 条 / 新晋升 K 条 / context 增量
- 省时刻: 哪次加载帮了忙
- 摩擦点: 哪次别扭 → 改了哪份 skill / 为什么
- 下周期偏向: 一句话
```

## 边界
- 本 skill 可以改 `AGENTS.md`、`skills/`、`scripts/` 和目录约定。
- 不直接改项目事实和个人长期资产内容；那些仍由「摄取」「执行」负责。
- 晋升 assets 前必须问主人确认。
