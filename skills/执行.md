# skill: 执行 —— 基于共享 context + 真实代码仓库完成任务

**触发**：主人说「执行 <项目名> <需求>」「改代码」「实现这个任务」等。

**目的**：结合共享项目 context 和真实代码完成任务；与主人确认计划、实施并验证。只保存后续会用到的过程和判断。

## 先读（重要：先读再动手）
1. `/opt/processes/context_platform/README.md` 和
   `/opt/processes/context_platform/AGENTS.md`。
2. 目标项目的共享 context，例如
   `/opt/processes/context_platform/projects/marvin/index.md`，再按 index 读取相关文档。
3. 真实代码仓库与表结构；共享 context 只给地图，代码从真实 repo 读取。

## 流程
1. 读相关共享 context 和代码后，复述目标、约束和已知 failure modes；与主人澄清歧义并商定可检验的计划。
2. 按计划做必要的实验或代码修改，运行有针对性的验证；根据结果调整下一步并说明未验证之处。
3. 如果本次过程、失败或待办值得回看，写 `worklog/<日期>-<项目>-<简述>.md`；简单任务不强制写。
4. 新的团队项目事实、正式决策、workflow 或坑，按共享仓库规则写入 `/opt/processes/context_platform`，默认用英文并更新目标 index；不要复制代码。
5. 如果主人明确要保存本次学到的个人判断，转到 `skills/判断.md` 讨论证据和边界，再更新 `judgments.md`；不自动提炼所有工作记录。

## 可选 worklog 格式
```
# <日期> · <项目> · <任务简述>

## Task
- 主人要完成什么。

## Context Used
- 读了哪些 context_platform context。
- 读了哪些代码路径。

## Changes / Output
- 改了什么或产出了什么方案。

## Shared Context Routed
- 哪些项目事实、决策、坑或 workflow 已写入 context_platform。

## Decisions / Pitfalls / Follow-ups
- 新决策、坑、待确认问题。

## Next Step
- 下一步需要确认或验证什么。
```

## 原则
- 不把共享项目 context 写回 `working-os/projects`；`working-os/projects` 不再作为项目 context 容器。
- 只回写「代码说不出来的东西」：为什么这么做、踩了什么坑、定了什么，不复述代码。
- 个人判断只在主人有意保存时写入 `judgments.md`；项目正式决定仍以共享 context 为准。
